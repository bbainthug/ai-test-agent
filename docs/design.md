# 设计文档

> 写给面试官 / 复核者看的设计说明：为什么这样设计、试过什么、数据说明了什么。
> 过程记录与逐次数字见 [`results.md`](results.md)；本页只讲决策与取舍。

## 1. 问题定义

用 LLM 生成端到端测试用例、再用 LLM 当裁判，最难的部分不是"生成"——一句话描述配合足够长的
提示词，模型总能吐出一份看起来合理的用例 JSON。真正难的是**可信**：

- 用例真的测到了目标功能吗，还是在到达目标接口之前就已经失败或走偏了？
- 裁判说 pass，是因为系统真的对，还是因为裁判本身不严格、或者被幻觉的"看起来对"糊弄过去？
- 同一句话描述，反复生成的用例是否稳定，还是每次都不一样、结论全凭运气？

这个项目把这三个问题拆成三件可独立测量的事——**覆盖**（用网络探针判断用例是否真的碰到了目标
接口，而不是"跑完了"就算数）、**裁判可信度**（用故障注入测漏报、用盲裁判/纯断言做消融对照）、
**一致性**（同一功能跑 5 轮看结论是否稳定）——数字见 `results.md` 的 Milestone B/B2。

## 2. 架构与模块职责

```
一句话功能描述
      │  agent/planner.py（可选先过 agent/explorer.py 探索真实页面）
      ▼
  用例 JSON（agent/schema.py 强制受限动作集）
      │  agent/executor.py（Playwright）
      ▼
  步骤日志 + 文本快照（agent/snapshot.py）+ 三分类失败原因
      │  agent/judge.py（LLM，只看文本快照）
      ▼
  pass / fail / unsure + 证据（引用快照行号）
      │  agent/report.py
      ▼
  reports/<run_id>.json + .md
```

| 模块 | 职责 | 关键约束 |
|---|---|---|
| `agent/schema.py` | 用例 JSON 的唯一 schema；受限动作集 `goto/click/fill/select/wait_for/assert_text/assert_visible/assert_url`（8 个，不许扩展） | 非法用例（未知动作、缺参数）在进入执行器前就被拒绝，不会"带伤运行" |
| `agent/explorer.py` | 只读探索真实页面：登录一次（复用 `storage_state`）、抓控制台侧边栏 + 前台导航生成站点地图、给定 URL 拍可访问性树快照 | 不装故障、不计入覆盖率、不写死任何路由表 |
| `agent/planner.py` | 一句话描述 → 用例 JSON；`mode="grounded"`（默认）先探索页面再写用例，`mode="baseline"` 是旧版本纯凭描述硬猜 | grounded 模式产出后做**静态选择器校验**（不跑浏览器），选择器在目标页面快照里找不到就回传 LLM 修一次 |
| `agent/executor.py` | 把用例 JSON 翻译成 Playwright 操作；选择器优先级 `role= > label= > text= > placeholder= > CSS`；每步失败归入 `assert_failed`/`locator_failed`/`timeout` 三类之一 | 支持故障注入（`Fault`：拦截指定接口返回 500）与网络探针（判断用例是否真的调用了目标接口） |
| `agent/snapshot.py` | 裁判的唯一视觉输入：页面的文本化可访问性树（不用截图、不做 OCR） | 超长截断并标注 `[TRUNCATED]`，写盘前统一脱敏 |
| `agent/judge.py` | LLM 裁判，三态 `pass/fail/unsure`；证据必须引用快照行号 | 输出解析失败或证据不足一律降级 `unsure`，绝不默认 `pass` |
| `agent/report.py` | 产出 `reports/<run_id>.json` + 同名 Markdown | README 里的每个数字都必须能从这些 JSON 复现 |
| `bench/` | 阶段 B 的 20 功能基准：`features.json`（功能 + 故障 + 参考用例）、`run_bench.py`（并发 runner）、`metrics.py`（覆盖率/误报率/漏报率/一致率）、`compare.py`（前后对比） | 前后对比时功能清单、指标口径、执行器、裁判均不改动（公平性红线） |

## 3. 关键决策与取舍

每条决策都配一条支撑数据或实例，避免空谈原则。

**受限动作集 + schema 校验。** 8 个动作、字段由 pydantic 强制，非法输出直接拒绝。
代价是显而易见的：`search-posts` 这个功能的搜索框必须按 `Enter` 才会触发过滤，而动作集里没有
"按键"这个动作——5 轮 B2 基准里 `search-posts` 全部判 `fail`，复核后发现是这个限制导致用例
结构上不可能测出真实结果，不是产品缺陷（细节见 [`results.md`](results.md#milestone-c-复核search-posts-不是-halo-缺陷是执行器动作集的限制)）。
这是"受限动作集换来可预测性、但会漏测某些交互模式"这条取舍的一个具体代价。

**三态裁判，不确定时给 `unsure`，不允许默认 `pass`。** 阶段 B 数据：健康系统上已覆盖的 53 次
运行里，`informed` 裁判 7 次给 `unsure`（证据不足时如实说不确定，而不是像纯断言那样机械通过）。
这个设计的价值在漏报侧最明显：10 次故障已触发的运行里，纯断言漏了 3 次（断言只检查了页面框架
文案，接口 500 时照样通过），`informed` 裁判 0 漏报——代价是误报率比纯断言高约 10 个百分点
（见 `results.md` Milestone B「读数」第 2 条）。

**只看文本快照（可访问性树），不用截图/多模态。** 成本与可复现性的取舍：文本快照能精确引用
"L72 行出现空态文案"这样的证据，截图裁判做不到逐行引用，且截图输入的 token/延迟成本远高于
文本。代价是纯视觉信息（颜色、布局错位）测不到——这类问题目前不在本工具范围内。

**用网络探针定义覆盖，不是"用例跑完了就算数"。** Milestone B 最重要的读数：按运行计只有
53% 的用例真正触达目标接口，另外近一半"跑完了"但没测到东西。如果不做这层区分，报告出来的
"通过率"会系统性地过于乐观。

**故障注入测漏报，而不是只测健康系统。** 每个功能配一个真实会命中的故障点（`bench/features.json`
的 `fault`），且先用参考用例在健康/故障两态各验证一次（`reference_validation.json`，20/20 通过），
证明故障在 UI 上确实可见——这样"漏报"才是裁判/用例的问题，不是"故障本身就测不出来"的问题。

**盲裁判、纯断言两组消融对照。** 单独看 `informed` 裁判的误报率（47.2% → 17.8%，B→B2）说明
不了 LLM 裁判本身的价值有多少来自"看得懂步骤结果"、多少纯粹是运气。盲裁判组（只给预期和最终
快照，不给步骤结果）误报率始终最高（77.4% / 62.2%），证明"看步骤结果"这个设计有效；纯断言组
在漏报上系统性地更差（30% / 5.6%），证明 LLM 裁判在漏报侧的价值不是噪音。

**grounded 探索：自动发现，不硬编码路由。** 站点地图靠点击侧边栏菜单项读跳转后的
`page.url` 得到（因为 Halo 控制台侧边栏是 `<li>` + 客户端路由，没有真实 `<a href>`），
不是写死一份路由表——换一个 Halo 版本（本次任务在 2.26.1 上验证过登录/设置页表单字段确实
变了：新增 `externalUrl`、字段标签从"用户名"变成"账号"）路由表会立刻过期，探索不会。
效果：覆盖率从 53% 提到 90%，`informed` 裁判误报率从 47.2% 降到 17.8%（详细对比表见
`results.md` B2 一节）。

**公平性红线：前后对比时功能清单、指标口径、执行器、裁判都不改。** B2 只改了 planner 的规划
方式（先探索再写用例），`bench/features.json`/`bench/metrics.py`/执行器/裁判逐字未动——否则
"覆盖率从 53% 到 90%"这类数字就说不清是 planner 变好了还是评分标准变松了。

## 4. 失败与教训

- **planner 编造路由**：baseline 模式下 planner 凭一句话描述硬猜 URL 和选择器，典型案例是把
  角色管理写成会 404 的 `/console/roles`（真实路由是 `/console/users` 下的一个标签页）。
  这是 grounded 模式存在的直接原因。
- **`assert_url` 竞态**：Milestone A 阶段执行器原来登录跳转后立即读 `page.url`，跳转未完成
  就判失败；改成轮询等待至超时后修复。这类"执行器自己的 bug 被真实运行暴露"正是闭环设计的
  意义——如果只跑单元测试，这个竞态不会被发现。
- **外联横幅导致 flaky**：Halo 控制台"新版本可用"横幅由浏览器实际请求
  `release-checker.halo.run` 决定是否出现，会盖住"发布"按钮，且是否出现取决于外网连通性；
  改成执行器按 `BLOCK_EXTERNAL_HOSTS` 屏蔽被测应用的外联域名（可配置关闭）。
- **并发下 `site_map` 竞态**：接手 B2 半成品实现时，`run_bench` 的多个规划线程共用探索结果，
  但当时是每线程一份 `Explorer`（`threading.local`），仍会在共享缓存目录上竞争写
  `site_map.json`。改成真的共用一个 `Explorer` 实例并加锁双检；补了单元测试验证
  "8 线程并发只应触发 2 次探索调用"，去掉锁会失败（变成 10 次）。
- **探索计时口径错误**：`grounding.explore_seconds` 一开始把两次 LLM 往返也算进"探索"耗时，
  导致 comparison.md 里那一行（19277.0s）比总墙钟还大，明显不对。修正为只在真正的浏览器探索
  调用周围计时；已跑的 100 条记录用 `calls.jsonl` 里的 `latency_ms` 反推校正（校正后
  100 次规划平均 4.66s/次），详见 `results.md`。

## 5. 局限与下一步

- **`>>` 链式选择器未覆盖“同名按钮”歧义**：文章编辑器页面"发布"按钮与"文章设置"确认弹窗里的
  "发布"按钮同名，`role=button[name="发布"]` 精确匹配到两个元素，Playwright strict mode 报错。
  选择器语法已支持 `role=dialog >> role=button[name="发布"]` 链式作用域，但静态校验只查
  "选择器在快照里存在"，不查"唯一性"，这类歧义会漏过校验、留到执行阶段才报错。下一步：静态
  校验里加一条"同名元素数 > 1 时警告"。
- **grounded 选页校验的漏洞**："LLM 选的 URL 必须来自站点地图"这条校验对裸 origin（如前台
  首页）基本不设防（`startswith` 天然满足）；实测中 `role-list` 选中过从未出现在站点地图里的
  URL，靠 Halo 客户端路由重定向蒙对。下一步：校验改成精确匹配站点地图条目集合，而不是前缀匹配。
- **多步向导类交互测不了**：受限动作集没有"按键"（如 `search-posts` 需要的 `Enter` 提交、
  多步弹窗里的键盘导航），也没有拖拽、文件上传等。下一步：评估是否值得为"提交式搜索"这一类
  常见模式加一个极窄的 `press` 动作（仍然只允许固定的几个键名，不开放自由键盘输入，维持受限
  动作集的可预测性）。
- **换语言 / 改版会批量失效**：选择器依赖简体中文界面文案（role/label/name）。本次在 2.26.1
  上验证：登录页字段标签从"用户名"变成"账号"、初始化表单新增必填字段 `externalUrl`——这类
  改动会让依赖旧文案/字段名的用例批量失效，属于选择器策略本身的取舍（可读性换来的脆弱性），
  不是 bug。
- **3 类功能因空数据/接口报错在 UI 上无法区分，已排除出基准**（评论列表、附件列表、仪表盘
  统计），这本身是 Halo 的一个可观测性问题，已写成 issue 草稿（未提交），见
  [`docs/issues/halo-empty-state-on-api-error.md`](issues/halo-empty-state-on-api-error.md)。
- **成本**：grounded 模式每次运行平均 23.5k tokens（比 baseline 的 14.3k 高约 64%），主要是
  多了一轮"探索 + 选页"LLM 调用；换来的是覆盖率 53%→90%、误报率 47.2%→17.8%。这笔取舍在
  当前场景下判断是值得的，但如果目标系统页面很大（如富文本编辑器，`publish-post` 这次两轮
  完全超时耗尽重试就是这个原因），额外这一轮往返本身也会成为新的失败来源。
